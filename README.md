---

A system with a voice amplifier and whitelist for VRChat worlds that is easy on the ears, doesn't get too loud, and can still be heard well globally.

Use the standalone whitelist or optionally connect it to **ProTV** or
**AccessTXL**. Neither integration is required for standalone use.

Comes with a [Minimal Amplifier](#MinimalAmplifier) package in the VCC listing if you only want the amplifier with no extra settings.

**Free for personal and commercial use with credit to Erallie.**
See [License and credits](#license-and-credits).

## Features

- Ear-friendly amplification
  - It isn't too loud when close
  - It's easy on the ears
  - It can still be heard well throughout the world.
- Multiple forms of amplification
  - Stage trigger-based amplification based on a whitelist
  - Microphone pickup amplification
  - Global amplification for a whitelisted user.
  - Minimal trigger-based amplification without access restrictions.
- Whitelist controls.
  - A standalone display-name whitelist.
  - Optional authorization of the first instance master.
  - Can optionally integrate with ProTV's or AccessTXL's whitelists.
- Shared object toggles with whitelist-controlled interaction.
  - Optional ownership transfer and object respawning.
- Local object and canvas visibility based on whitelist status.
- Optional control of ProTV's shared volume setting.
- Toggleable staff tags that hover above your head.
- Custom inspectors with script descriptions, field help, and reference search buttons.
- Tools menu for adding prefabs, opening example scenes, and assigning scene references.

## Installation

Start with a VRChat Worlds project managed through the VRChat Creator
Companion, with the Worlds SDK and UdonSharp available.

### Through VCC

Add the listing to VCC [here](https://vcc.gozarproductions.com/), then add
**Stage Amplifier and Whitelist** to your world project.

### Manual installation

Copy the package into:

`Packages/com.erallie.stage-amplifier`

A release package ZIP contains the package's contents. Extract those
contents into the directory above.

Allow Unity to finish importing and compiling UdonSharp before
configuring the components.

## Quick setup

1. Open **Tools > Erallie > Stage Amplifier and Whitelist**.
2. Use **Open Example Scene** for a starting example, or use **Add to Scene**
   to add the Whitelist, Stage Amplifier, microphones, and controls you need.
3. On **Whitelist**, enter exact VRChat display names and optionally enable
   **Include First Instance Master**.
4. For optional integrations, add the corresponding bridge and configure it
   using the [integration instructions](#optional-integrations).
5. Run **Assign All Scene References** from the Tools menu.
   Review its report and resolve missing or ambiguous matches using individual
   **Find** buttons or manual assignments.
6. Configure the stage trigger, separate barrier collider, and teleport destination in the **Stage Amplifier** script. These scene-specific references still need your own choices.
7. Check **Listeners** on Whitelist. Use **Find and Add Whitelist Listeners**
   when adding additional supported components.
8. Save, then test in ClientSim and in a multi-client VRChat instance.

Copy example scenes into `Assets` before customizing and saving them so package
updates do not overwrite your work. Added prefabs remain linked prefab instances;
scene edits are overrides unless you explicitly apply them to the prefab asset.

## Tools menu and inspector helpers

Menu root: **Tools > Erallie > Stage Amplifier and Whitelist**.

| Action | Purpose |
| --- | --- |
| Add to Scene | Adds configured example prefabs to the active scene |
| Open Example Scene | Opens example scenes for your reference to copy in your own scene |

## Stage access rules

The intended behavior is:

| Stage state | Whitelisted players | Unwhitelisted players |
| --- | --- | --- |
| Normal access, empty | May enter | May enter |
| Normal access, occupied | May enter | Blocked unless already the current performer |
| Whitelist-only access | May enter | Blocked |

Whitelist-only access and global shutdown are separate controls:

- `StageWhitelistToggle` switches the stage's access mode.
- `WhitelistedToggle` enables or disables its assigned objects.

The current implementation tracks one `CurrentPerformer` name.
A whitelisted player may occupy that slot, while other whitelisted
players bypass the occupancy restriction. There is no separate queue
of unwhitelisted performers.

## Components

### Whitelist

Determines whether a player is authorized.

A player is authorized when any configured source permits them:

- The ProTV bridge recognizes them as an authorized user or superuser.
- The TXL bridge's assigned Access Control grants them access.
- Their display name exactly matches a local whitelist entry.
- **Include First Instance Master** is enabled and their name matches
  the initially recorded owner.

Local display-name matching is case-sensitive.

The initial owner name is recorded once through `OnPlayerJoined` by
the owner of the whitelist object. It is not replaced when the
instance master changes.

Keep the whitelist object enabled. It sends `WhitelistUpdated` to its listeners at startup, after recording
the initial owner, and whenever `UpdateUI()` is called.

Both integration bridges notify this Whitelist directly. Custom scripts that
change authorization should call `Whitelist.UpdateUI()` after their change.

**Find and Add Whitelist Listeners** searches the current scene, including
inactive objects, for these supported component types:

- `GlobalAmplifier`
- `StageAmplifier`
- `StageWhitelistToggle`
- `ToggleWhenWhitelisted`
- `VolumeSyncToggle`
- `WhitelistedToggle`

It preserves existing entries, fills empty slots, and avoids duplicates. Review the
list when your scene deliberately uses more than one Whitelist.

The **Assign This Whitelist Throughout Scene** button assigns this component
to serialized Whitelist fields throughout the scene, replacing existing
assignments and supporting Undo.

### StageAmplifier

Amplifies players inside its trigger and manages stage access.

Requires a trigger `Collider`.

| Setting | Purpose |
| --- | --- |
| Whitelist | Determines authorization and occupancy bypass |
| Barrier Collider | Separate physical collider controlling local entry |
| Teleport On Kick Transform | Destination for rejected players |
| Mesh To Hide | Optional renderer hidden for the local performer |
| Canvas To Hide | Optional canvas hidden for the local performer |
| Voice Multiplier | Voice-distance multiplier; default `17` |
| Starting Volume | Minimum voice far distance; default `25` |
| Limit Amplification Range | Whether to stop amplification past a certain distance |
| Limit Distance | Distance where amplification stops |

`WhitelistOnly` selects the access mode.

`CurrentPerformer` records the occupied slot.

Changing either property refreshes barrier state through
`WhitelistUpdated()`.

Exiting, respawning, or leaving resets the player's voice settings
and clears the slot if they were the recorded performer.

### StageWhitelistToggle

Lets whitelisted players switch a linked stage between normal
access and whitelist-only access.

Assign:

- The whitelist.
- The linked `StageAmplifier`; use its **Find** button to locate one in the scene.
- Optional mesh visibility and interaction text settings.

Use a trigger collider for in-world interaction.

Interaction takes ownership of the control and linked stage, changes
their access state, and requests serialization.

This control does not globally disable the stage.

### Microphone

Amplifies the voice of the player holding the pickup.

Requires a `VRCPickup` component.

Configure the pickup's collider and Rigidbody as appropriate.
Dropping the microphone resets voice settings.

The microphone itself does not check whitelist authorization.
Control its availability through a separate `Whitelisted Toggle` component
when needed.

For synchronized movement and respawning through `WhitelistedToggle`,
place `VRCObjectSync` on the exact GameObject being toggled.

### GlobalAmplifier

Lets a whitelisted user interact to amplify their voice wherever
they move.

Requires a trigger `Collider`.

The object's owner is the amplified player. The owner can switch
amplification off, and ownership changes also clear amplification.

Each instance of this script in-world supports one amplified user at a time.

**Hide Mesh If Not Whitelisted** optionally hides the control's
renderer from unauthorized players.

### MinimalAmplifier

Amplifies players inside a trigger without whitelist or occupancy
restrictions.

Requires a trigger `Collider`.

Exiting, respawning, leaving, or disabling the component resets
voice settings.

### WhitelistedToggle

Lets whitelisted players toggle assigned objects using a shared
synced state.

Requires a trigger `Collider`.

| Setting | Behavior |
| --- | --- |
| Whitelist | Authorization source; missing reference disables interaction |
| Hide Mesh If Not Whitelisted | Hides the control's renderer locally |
| Objects To Toggle | Objects enabled or disabled by shared state |
| Transfer Ownership | Takes ownership of explicitly listed targets |
| Child Objects | Additional ownership targets |
| Respawn On Disable | Respawns eligible targets when toggled off |
| Menu Toggle | Optional Unity UI Toggle reflecting shared state |
| Customize Interaction Text | Enables state-dependent interaction text |
| Interact Text When On | Text shown while objects are enabled |
| Interact Text When Off | Text shown while objects are disabled |

**Child Objects** appears only when **Transfer Ownership** is checked.

**Customize Interaction Text** defaults to unchecked. When unchecked,
the script leaves the existing interaction text untouched.

When checked, **Interact Text When On** and **Interact Text When Off**
appear in the inspector. The script selects the appropriate text
according to the shared toggle state.

Ownership transfer does not automatically discover all descendants.
Add any additional ownership targets explicitly.

Respawning requires `VRCObjectSync` on each exact target in
**Objects To Toggle**. It runs for locally owned targets when the
toggle controller is locally owned.

Respawning may take ownership of target objects even when
**Transfer Ownership** is unchecked.

The `Menu Toggle`'s state is updated with `SetIsOnWithoutNotify` and only called when the objects are toggled.

Initial state comes from the first non-null target's `activeSelf`.

Keep the controller outside the hierarchy it disables so users can
turn the objects back on.

### ToggleWhenWhitelisted

Shows or hides assigned objects locally according to the local
player's authorization.

- **Toggle On** checked: objects and canvasses are enabled for whitelisted players.
- **Toggle On** unchecked: objects and canvasses are disabled for whitelisted players.

Keep this component on a separate, always-active controller rather
than on the whitelist object or an object it disables.

### ToggleOthersOnActiveSelf

Enables assigned objects locally when this component is enabled,
and disables them when it is disabled.

It performs no whitelist checking or synchronization itself.

### VolumeSyncToggle

Lets authorized players change ProTV's shared volume-control setting.

Requires a trigger `Collider`.

With ProTV installed, assign:

- The whitelist.
- The ProTV `TVManager`.

The component controls `TVManager.syncVolumeControl`.

Without ProTV, its TV manager field is excluded and interaction has
no effect on a TV system.

### StaffTag and StaffTagToggle

Shows a floating staff tag above a player's head. Each whitelisted player can
show or hide their own tag independently using `StaffTagToggle`.

The Staff Tag follows its assigned player's head with a **Vertical Offset** in meters (configurable in Unity).

If a player leaves the world with their staff tag shown, it will be retained when they rejoin the world.

Do not add `VRCObjectSync` to the tag prefab: the script calculates its local
position and rotation.

Keep `StaffTagToggle` in Whitelist's listener array so permission changes trigger its revocation checks.

## Voice settings

The amplifiers feature a unique way of boosting your voice that's easy on the ears, not too loud when up close, and still heard well throughout the world.

They do this by adjusting the voice falloff range according to the distance between you and the person being amplified.

The amplifiers calculate voice far distance using:

```text
max(Voice Multiplier × distance from listener to speaker, Starting Volume)
```

Defaults:

- **Voice Multiplier:** `17`
- **Starting Volume:** `25`

**Starting Volume** controls the minimum voice far distance.

Amplification disables voice low-pass filtering.

Resetting restores voice far distance to `25` and re-enables low-pass
filtering. It does not restore custom settings from another system.

Using scripts from other voice amplication systems to amplify the same player can overwrite each other's settings. Test combinations of microphones, stages, and other voice scripts together.

## Optional integrations

Integrating with ProTV or AccessTXL allows people whitelisted through their system to be treated as whitelisted in our system; your own whitelist entries in our whitelist script remain whitelisted, and the option to auto-whitelist the first instance master for our system is set in our own whitelist. Neither ProTV nor TXL is required for the Stage Amplifier to function.

### ProTV

1. Install ProTV and its dependencies separately.
2. Add the **ProTV Whitelist Bridge** prefab or component.
3. On `ProTVWhitelistBridge`, assign ProTV's **TV Whitelist** and your
   **Whitelist** component in **Update Listener**.
4. Assign this bridge to **Pro TV Access Bridge** on Whitelist.
5. Populate Whitelist's listener list and test granting and revoking access.

The bridge accepts ProTV authorized users and superusers and forwards ProTV
permission-change notifications to `Whitelist.UpdateUI()`.

**VolumeSyncToggle** is ProTV-only. Assign its Whitelist and ProTV `TVManager`
to control `syncVolumeControl`. It does not synchronize VideoTXL volume.
Without ProTV installed, the bridge grants no extra access and volume-sync
interaction has no effect on a TV system.

### AccessTXL

1. Install AccessTXL and its CommonTXL dependency separately.
2. Configure a TXL **Access Control** component. Enable **Enforce** and
   **Allow Whitelist** for whitelist-based restrictions, and leave
   **Allow Everyone** off when testing individual permissions.
3. For runtime grants, connect the relevant **Dynamic Whitelist** to the Access
   Control's **Whitelist Sources**. Configure the grant controls to update that
   same source. Its Sync Player List's access settings determine who may grant
   access; they may use a separate administrator Access Control.
4. Add the **AccessTXL Whitelist Bridge** prefab or `TXLWhitelistBridge` component.
5. Assign the intended **TXL Access Control** and your **Whitelist** component
   in the bridge's **Update Listener** field.
6. Assign the bridge to **Txl Access Bridge** on Whitelist.
7. Populate Whitelist's listeners and test granting and revoking access.

### Existing scenes using WhitelistUpdateListener

The script Whitelist Update Listener has been embedded directly into the Whitelist script. If you set up this VCC package before version 0.1.0, you must transfer its listener entries to **Whitelist > Listeners**, or collect the
supported components with **Find and Add Whitelist Listeners**. Point both
bridges' **Update Listener** references to the Whitelist component, then remove
the old listener component. Preserve any additional custom listener entries.

## Troubleshooting

| Problem | Check |
| --- | --- |
| Whitelisted player blocked by an occupied stage | Confirm the stage's whitelist reference, rerun Find and Add Whitelist Listeners on `Whitelist`, and inspect other barrier controllers. |
| Interaction text does not change with toggle state | Enable Customize Interaction Text and configure both text fields. When disabled, existing interaction text is intentionally left untouched. |
| Wrong whitelist assigned across the scene | Undo the scene-wide assignment with `Ctrl + Z`, then assign individual references when multiple whitelists are intentional. |
| Control cannot be used | Check its whitelist reference, exact display name, collider, and listener refresh. |
| First master not recognized immediately | Check Include First Instance Master, Whitelist listener assignments, and initialization order. |
| Player not teleported offstage | Assign Teleport On Kick Transform and confirm the stage trigger is active. |
| Microphone does not respawn | Enable Respawn On Disable and add VRCObjectSync to the exact toggled object. |
| Staff tag does not appear | Assign Whitelist and a prefab with StaffTag on its root; confirm access, compile UdonSharp, and check the Console. |
| Staff tag stays after access is revoked | Confirm StaffTagToggle is in Whitelist's Listeners and the integration bridge notifies that Whitelist. Check whether another access source still authorizes the player. |
| Staff tag does not return after rejoining | Confirm the same instance and display name, remaining whitelist access, and that the tag was not toggled off or revoked. |
| ProTV fields missing | Make sure that ProTV is installed in the project, then allow Unity to recompile. |
| Compile errors after removing an integration | Restore the current package files, including fallback scripts, runtime assembly definitions, UdonSharp registration assets, and Program Assets. Allow Unity and UdonSharp to recompile. |
| Automatic assignment leaves fields empty | Check the Console for zero or multiple matches; add the missing component or use the field's Find button to select a candidate. |
| TXL grants do not update visibility | Check the Dynamic Whitelist source, Allow Whitelist, bridge Access Control, bridge Update Listener pointing to Whitelist, and the affected control in Whitelist's Listeners array. |
| Different clients see different states | Check ownership, synchronization mode, late joining, and serialization. |
| Disabled objects cannot be re-enabled | Keep the toggle controller outside the hierarchy it disables. |

Missing-reference checks skip unavailable operations. They cannot
provide the feature associated with the missing reference.

ClientSim alone does not verify multi-client behavior. Test ownership,
synchronization, access rules, and late joining in VRChat.

This system controls world interactions; it is not a security boundary
against modified clients.
